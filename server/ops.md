# نگهداریِ سرور — چه چیزی کجا

همه‌چیزِ این صفحه روی خودِ سرور است، نه در مخزن: هیچ توکنی این‌جا نیست.

## کرون

```cron
# پشتیبانِ ساعتی (از قبل بود)
0  * * * * bash /opt/sltech/app/server/backup.sh      >/dev/null 2>&1
# نگهبان: پشتیبان تازه است؟ دیسک جا دارد؟ سرویس بالاست؟
*/10 * * * * bash /opt/sltech/app/server/ops.sh check   >/dev/null 2>&1
# آزمونِ بازیابی: آخرین پشتیبان واقعاً باز می‌شود؟
17 4 * * *   bash /opt/sltech/app/server/ops.sh restore >/dev/null 2>&1
```

خبرها از همان رباتی می‌روند که پشتیبان‌ها می‌روند
(`node server/index.js --notify "…"`). یک ایراد فقط **یک بار** خبر
می‌دهد و تا درست نشود ساکت می‌ماند — وگرنه یک دیسکِ پر یعنی صد پیام
در روز و بعدش کسی پیام‌ها را نمی‌خواند.

## دستورهایی که لازم می‌شوند

| کار | دستور |
|---|---|
| استقرارِ نسخهٔ تازه | `bash /opt/sltech/app/server/update.sh` |
| برگشت یک قدم عقب | `bash /opt/sltech/app/server/rollback.sh` |
| برگشت به نسخهٔ معین | `bash /opt/sltech/app/server/rollback.sh <sha>` |
| فهرستِ نسخه‌ها | `bash /opt/sltech/app/server/rollback.sh --list` |
| چکِ دستیِ سرور | `bash /opt/sltech/app/server/ops.sh check` |
| آزمونِ بازیابی | `bash /opt/sltech/app/server/ops.sh restore` |
| پشتیبانِ رمزشدهٔ فایلِ کلیدها | `bash /opt/sltech/app/server/ops.sh env` |
| یک نوبت یادآور با دست | `node /opt/sltech/app/server/index.js --remind-now` |
| نبضِ سرویس | `curl -s localhost:8787/healthz` |
| خاموش کردنِ ورودِ دومرحله‌ای (وقتی ربات نرسید) | `node /opt/sltech/app/server/index.js --admin-2fa off` |
| روشن کردنش از سرور | `node /opt/sltech/app/server/index.js --admin-2fa on` |

## فایلِ کلیدها

`/etc/sltech/env` تنها جایی است که توکن‌ها در آن هستند و **پشتیبانِ
دیتابیس شاملش نمی‌شود**. ماهی یک بار:

```sh
bash /opt/sltech/app/server/ops.sh env
```

یک فایلِ `.enc` در `/var/backups/sltech/env/` می‌سازد (AES-256 با رمزی
که خودتان می‌دهید). آن را جایی **بیرونِ همین سرور** نگه دارید؛ وگرنه
با رفتنِ سرور، هم کلیدها می‌روند هم پشتیبانشان.

برگرداندن:

```sh
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in env-….enc -out env
```

## پشتیبانِ بیرونِ سرور (پارس‌پک)

هفتگی، روی زیرساختِ خودِ پارس‌پک. این همان چیزی است که پشتیبانِ محلی
هیچ‌وقت نمی‌توانست بدهد: نسخه‌ای که با رفتنِ دیسکِ همین سرور نمی‌رود.

دو لایه‌اند و کارشان یکی نیست:

| | پشتیبانِ محلی | پشتیبانِ پارس‌پک |
|---|---|---|
| هر چند وقت | ساعتی، به‌علاوهٔ یک نسخهٔ روزانه | هفتگی |
| کجا | همین دیسک | بیرونِ سرور |
| چقدر عقب | ۷ روز ساعتی، ۳۰ روز روزانه | به سیاستِ پارس‌پک |
| به چه درد | اشتباهِ امروز و این هفته | رفتنِ خودِ سرور |

یعنی برای برگرداندنِ «دیروز ردیفی پاک شد» باز هم پشتیبانِ محلی
جواب می‌دهد، نه نسخهٔ هفتگی. آن یکی کفِ ماجراست، نه راهِ روزمره.

### از نسخهٔ پارس‌پک چه چیزی را برگردانیم

**به `/var/lib/sltech/sltech.db` داخلِ آن نسخه دست نزنید.** آن فایلِ
زندهٔ لحظهٔ عکس‌برداری است و ممکن است وسطِ نوشتن گرفته شده باشد —
عکسِ فایل‌سیستمی از یک SQLiteِ در حالِ کار می‌تواند نیمه‌کاره دربیاید.
آنچه در همان نسخه قابلِ اعتماد است `‎/var/backups/sltech/sltech-*.db.gz‎`
است: این‌ها با `sqlite3 .backup` گرفته شده‌اند و `PRAGMA integrity_check`
هم رویشان خورده. پس ترتیب این است:

```sh
systemctl stop sltech
ls -t /var/backups/sltech/sltech-*.db.gz | head -1     # تازه‌ترین سالم
gunzip -c /var/backups/sltech/sltech-<همان>.db.gz > /var/lib/sltech/sltech.db
chown sltech:sltech /var/lib/sltech/sltech.db
sqlite3 /var/lib/sltech/sltech.db "PRAGMA integrity_check;"   # باید ok بدهد
systemctl start sltech
```

پیوست‌ها جدا هستند و در `‎$BACKUP_DIR/files‎` آینه شده‌اند؛ همان‌جا از
نسخهٔ پارس‌پک برمی‌گردند.

### دو چیز که باید دانست

**فایلِ کلیدها حالا در نسخهٔ بیرونی هم هست.** اگر پشتیبانِ پارس‌پک
عکسِ کلِ دیسک باشد (حالتِ معمول)، `‎/etc/sltech/env‎` هم داخلش است — یعنی
با رفتنِ سرور دیگر کلیدها نمی‌روند. در عوض توکن‌ها حالا یک جای دیگر هم
وجود دارند. رسمِ ماهانهٔ `ops.sh env` بی‌خود نشده، ولی دیگر تنها راه
نیست.

**این مسیر هنوز یک بار هم آزمایش نشده.** پشتیبانِ محلی هر شب خودش را
امتحان می‌کند (`ops.sh restore`)؛ نسخهٔ پارس‌پک هیچ‌وقت برگردانده نشده.
تا آن روز، «پشتیبانِ بیرونی داریم» یک فرض است نه یک واقعیت — همان
اشتباهی که دربارهٔ پشتیبانِ محلی نکردیم.

دو چیز را هم از خودِ پارس‌پک بپرسید، چون سیاستش دستِ ماست نه کدِ ما:
چند نسخه نگه می‌دارد، و عکس از کلِ دیسک است یا فقط بخشی.

## وقتی چیزی خراب شد

۱. `bash server/ops.sh check` — کدام تکه خراب است؟
۲. `journalctl -u sltech -n 50 --no-pager` — چرا؟
۳. اگر استقرارِ تازه خرابش کرده: `bash server/rollback.sh`
۴. اگر داده خراب شده: آخرین پشتیبان در `/var/backups/sltech/`،
   و مسیرِ برگرداندنش در `server/CUTOVER.md`.
۵. اگر خودِ سرور رفته: نسخهٔ هفتگیِ پارس‌پک — بخشِ بالا می‌گوید از
   داخلش کدام فایل را باید برداشت و کدام را نباید.

## ورودِ دومرحله‌ای پنلِ ادمین

پیش‌فرض خاموش است. در پنل: **کلیدها و رمز ادمین ← ورود دومرحله‌ای**.
روشن که باشد، بعد از رمز یک کدِ شش‌رقمی به همان گفتگوی تلگرامیِ
پشتیبان‌ها می‌رود (ده دقیقه، پنج تلاش، یک‌بارمصرف).

اگر روزی ربات از کار افتاد و کد نرسید، از روی سرور خاموشش کنید؛
دستور در جدولِ بالاست. کسی که به سرور دسترسی دارد، این قفل برای او
نبوده.

## کارتابلِ نمایشی

هر کارتابلی که آدرسش `demo` باشد نمایشی است: بی‌رمز باز می‌شود، هرچه
در آن نوشته شود **روی سرور نمی‌نشیند** (فقط در مرورگرِ خودِ بازدیدکننده
می‌ماند) و نوارِ «نسخهٔ نمایشی» پایینش دیده می‌شود.

ساختنش مثل هر کارتابلِ دیگری است — در پنل، «کارتابل تازه» با آدرسِ
`demo`. بعدش یک بار خودتان واردش شوید و چند ردیفِ نمونه بنویسید…
ولی توجه: چون نوشتن در کارتابلِ نمایشی ذخیره نمی‌شود، دادهٔ نمونه را
باید از همین راه بگذارید:

```sh
# نمونه‌ای که در مرورگر ساخته‌اید را به‌شکل JSON ذخیره کنید، بعد:
sqlite3 /var/lib/sltech/sltech.db \
  "INSERT INTO kartabl(k,v,rev,updated) VALUES('demo:state', readfile('demo.json'), 1, strftime('%s','now')*1000)
   ON CONFLICT(k) DO UPDATE SET v=excluded.v;"
```

(کلیدِ دقیقِ `state` هر کارتابل در `cfg.keys.state` همان ردیفِ
`planners` است.)

صفحهٔ اصلیِ سایت از دو جا به `/demo/` لینک دارد: نوارِ بالا و دکمهٔ
سرصفحه. **تا وقتی کارتابلی با آدرسِ `demo` ساخته نشده باشد، هر دو لینک
پنهان‌اند** — پیش از این نبودند و دکمه به صفحهٔ ۴۰۴ می‌رفت. صفحهٔ خانه
۵ دقیقه کَش می‌شود، پس بعد از ساختنِ کارتابلِ نمایشی تا ۵ دقیقه صبر
کنید (یا کَشِ کلادفلر را پاک کنید) تا دکمه پیدا شود.

## پشتیبان‌های ۳ تا ۸ آبان ۱۴۰۵: فایلِ HTML بی‌استایل باز می‌شود

در آن بازه، فایلِ HTMLِ داخلِ پشتیبان CSS و جاوااسکریپتش را همراه
نداشت و بی‌استایل — و بی هیچ داده‌ای روی صفحه — باز می‌شد.

(از ۸ آبان، فایلِ HTMLِ پشتیبان دوباره خودکفاست: CSS و جاوااسکریپت
داخلِ خودش هستند، پس حتی اگر از داخلِ زیپ و بی اکسترکت بازش کنید هم
خوانده می‌شود. قلم و نمودار فایلِ کنارند و با اکسترکت می‌آیند.)

**هیچ داده‌ای گم نشده.** هر پشتیبان سه فایل دارد و هر سه سالم‌اند:
`…-داده.json` و `…-دیتابیس.xlsx` دست‌نخورده‌اند، و دادهٔ کاملِ همان
کارتابل داخلِ خودِ فایلِ HTML هم هست، در بلوکی به نامِ `KARTABL_SEED`.
چیزی که نبود، نمایشگرش بود.

## این فایلِ پشتیبان سالم است؟

```sh
node /opt/sltech/app/server/bkcheck.mjs <پشتیبان.zip>
```

نه رمز می‌خواهد نه مرورگر نه سرور. برای هر کارتابل می‌گوید داده هست و
چند ماه، صفحه خودکفاست یا نه، ارجاعِ بازمانده‌ای دارد یا نه، و فایلِ
داده و اکسلش سرِ جایشان هستند یا نه.

روی پشتیبانِ سالم: «✅ … همه سالم». روی پشتیبانِ آن بازه: «⚠️ خودکفا
نیست» و نامِ همان فایلی که کم است.

برای قابلِ دیدن کردنشان:

```sh
# یک پشتیبانِ تازه از پنل بگیرید (دکمهٔ «🗂 پشتیبان همه، همین حالا»)
cd /opt/sltech/app
node server/bkfix.mjs <پشتیبانِ-قدیمی.zip> <پشتیبانِ-تازه.zip> <پوشهٔ-خروجی>
```

دادهٔ خروجی بایت‌به‌بایت همان دادهٔ فایلِ قدیمی است؛ فقط نمایشگرش از
پشتیبانِ تازه می‌آید. به فایل‌های ورودی و به سرور دست نمی‌زند.

چرا نمایشگرِ تازه و نه وصله کردنِ همان فایل: نامِ فایل‌های CSS و JS از
روی محتوایشان ساخته می‌شود و با هر استقرار عوض می‌شود، پس نامی که
فایلِ قدیمی صدا می‌زند دیگر وجود ندارد.
